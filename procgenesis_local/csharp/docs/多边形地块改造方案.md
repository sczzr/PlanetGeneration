# 多边形地块改造方案

> 参考基准：Azgaar / Fantasy-Map-Generator（下称 FMG）的 `src/generators/grid-generator.ts` + `voronoi.ts` + `generation-pipeline.ts`
> 目标工程：`procgenesis_local/csharp`（Godot 4.7.2 mono / C#，PlanetGeneration）
> **当前进度：P0（几何核心）+ P1（双向桥 + 接线）+ P2（交互迁移）+ P3（渲染接管）+ P4 第一阶段（地貌与河流地块化、地图单元格化）已完成并验证。**
> **当前默认模式是 `Cells`：游戏地图以多边形单元格呈现。** 连续场图层按地块采样值平铺。
> `PolygonTileMode.Raster` 可一键退回改造前的全部行为。

## 0. 结论速览

| 问题 | 结论 |

## 1. 现状盘点：当前"地块"是什么

### 1.1 证据

| 位置 | 事实 |
| --- | --- |
| `WorldGen/Types.cs` | 只有枚举与结果容器（`BiomeType`、`PlateResult`、`WorldStats`…），**没有任何 Tile / Cell / Polygon 类** |
| 全部生成器签名 | `Generate(int width, int height, ...)`，输入输出都是 `float[,] / int[,] / BiomeType[,]` |
| `WorldRenderer.Render` | 逐像素 `Parallel.For(0, height)` → 写 `byte[] buffer` → `Image.CreateFromData`。**渲染单元 = 像素** |
| `Main.State.cs` | `GeneratedWorldData` 持有 8 个二维数组；`MapWidth=256 / MapHeight=128`，输出固定 `4096×2048` |
| `Main.Lore.Interaction.cs` | 拾取：`tX = local.X / textureSize.X` → `sampleX = (int)(tX * MapWidth)`。**交互单元 = 像素** |
| 邻接 | 到处硬编码 8 邻域 `for oy in -1..1 / for ox in -1..1`（`ClassifyLandform`、`RiverGenerator.SelectNextCell`、`BuildOrogenyMask`…） |
| 环绕 | X 方向周期性（`WrapX`），Y 方向钳制 → **等距圆柱投影，经度 360° 环绕** |
| 缓存 | `WorldGenerationAlgorithmVersion = 3`，`PersistedWorldData` 直接序列化全部二维数组 |

### 1.2 结论

当前系统里"一个像素就是一个地块"。要引入多边形地块，**不是替换一个类，而是新增一个层级**，并决定哪一层是"真源"。

## 2. FMG 的做法（对照基准）

### 2.1 关键实现

```
getSpacing(cellsDesired, w, h) = round(sqrt(w * h / cellsDesired), 2)
getJitteredPoints(w, h, spacing):
    radius = spacing / 2;  jittering = radius * 0.9
    for y in radius..h step spacing:
        for x in radius..w step spacing:
            points.push([x + jitter, y + jitter])       // 抖动方格
getBoundaryPoints(w, h, spacing):
    offset = -spacing;  bSpacing = spacing * 2
    沿四边每 bSpacing 放一个伪点                         // 只裁剪，不生成地块
calculateVoronoi(points, boundary):
    Delaunator.from(points + boundary)                  // Delaunay 半边结构
    → cells.v (多边形顶点 id 序列)
    → cells.c (相邻地块 id，已过滤边界点)
    → cells.b (是否边界地块)
    → vertices.p (Voronoi 顶点坐标 = 三角形外心)
    → vertices.v / vertices.c
findCell(x, y):                                          // O(1) 拾取
    floor(min(y / spacing, cellsY - 1)) * cellsX + floor(min(x / spacing, cellsX - 1))
findAll(x, y, radius):                                   // 环形 BFS
    found = [findCell(x, y)]; 然后沿 cells.c 扩 ring
getPolygon(cellId) = cells.v[cellId].map(v => vertices.p[v])
```

### 2.2 值得照搬的四点

1. **抖动方格取点**：点数稳定、无空洞、天然避开严格共圆（退化），且 `findCell` 能 O(1) 反查。
2. **边界伪点**：解决"最外圈多边形无限延伸"的经典问题。
3. **`cells.v / cells.c / vertices.p` 三分量**：多边形几何与邻接拓扑分离，属性另存（FMG 用 `Float32Array / Uint8Array` 平铺 = SoA）。
4. **分层 `grid` / `pack`**：粗层做地块属性，细层做细节。本项目可类比为 `PolygonGrid` / 现有栅格。

### 2.3 不能照搬的一点

FMG 是**平面地图**（边界伪点即地图边缘）。本项目 **X 方向环绕**，跨缝两侧必须是同一个地块的邻居。
→ 必须做**镜像点**（见 §5.3），否则河流、文明扩散、地形掩膜都会在经度 0° 处断裂。

## 3. 目标架构：三层

```
┌─ 场层 Field（保留，不改算法）─────────────────────────────┐
│  float[,] elevation / temperature / moisture / river      │
│  Vector2[,] wind        BiomeType[,] biome  …             │
│  职责：连续场、噪声细节、4096×2048 贴图输出                │
│  14 个生成器全部留在这里，一行不改                          │
└──────────────────────────────────────────────────────────┘
              ↓ SampleFromRaster（生成期，一次性）
┌─ 地块层 PolygonGrid（新增，唯一的地块实体）───────────────┐
│  Points[] / Vertices[] / Cells{V,C,B}                     │
│  PolygonFields（SoA）：Height/Temperature/Moisture/       │
│  River/Biome/Rock/Ore/PlateId/Ecology/Civilization/       │
│  PolityId/CityId/Downslope …                              │
│  职责：属性归属、面积、质心、下游方向、区域归属            │
└──────────────────────────────────────────────────────────┘
              ↓ SplatToRaster（按需，给旧消费者）
              旧 `float[,]` 视图（WorldRenderer 旧重载 / StatsCalculator / Minimap）
```

**真源声明**：多边形层是地块属性的真源；栅格是它的投影。旧代码通过 `SplatToRaster` 拿到投影继续工作，因此"原有功能"不依赖任何重写。

## 4. 数据结构

### 4.1 拓扑（对齐 FMG 的 `cells.v / cells.c / cells.b`）

```csharp
namespace PlanetGeneration.WorldGen.Polygon;

/// <summary>多边形地块网格：一次生成、之后只读。取代"像素即地块"的旧模型。</summary>
public sealed class PolygonGrid
{
    public float Spacing { get; init; }        // 抖动前的点距（源栅格像素单位）
    public int CellsX { get; init; }           // 规则方格列数（O(1) 拾取用）
    public int CellsY { get; init; }           // 规则方格行数
    public int SourceWidth { get; init; }      // 源栅格宽（经度方向，环绕）
    public int SourceHeight { get; init; }     // 源栅格高（纬度方向，不环绕）

    public Vector2[] Points { get; init; }     // 地块中心点（抖动方格）
    public Vector2[] Boundary { get; init; }   // 边界伪点，不生成地块
    public CellTopology Cells { get; init; }   // v / c / b
    public VertexTopology Vertices { get; init; }
    public float[] Area { get; init; }         // 多边形面积（鞋带公式），人口/权重用
    public Vector2[] Centroid { get; init; }   // 多边形质心，标签/城市标记定位用
    public PolygonFields Fields { get; init; } // 所有属性（SoA）

    public int Count => Points.Length;

    public int FindCell(float x, float y);                 // O(1)
    public int[] FindAll(float x, float y, float radius);  // 环形 BFS
    public Vector2[] GetPolygon(int cellId);               // 顶点坐标序列
}

/// <summary>地块级拓扑。</summary>
public sealed class CellTopology
{
    public int[][] V { get; init; }  // 每个地块的多边形顶点 id 序列（首尾不重复）
    public int[][] C { get; init; }  // 相邻地块 id（跨经度缝的邻居已包含）
    public bool[]  B { get; init; }  // 是否贴着纬线边界（南北极圈）
}

/// <summary>顶点级拓扑（Voronoi 顶点 = Delaunay 三角形外心）。</summary>
public sealed class VertexTopology
{
    public Vector2[] P { get; init; } // 顶点坐标
    public int[][] V { get; init; }   // 相邻顶点
    public int[][] C { get; init; }   // 该顶点周围的地块（内部点恰好 3 个）
}
```

### 4.2 属性（SoA 平铺，性能对齐 FMG 的 typed array）

```csharp
/// <summary>地块属性集合。用并列数组而非结构体数组：并行遍历友好、序列化紧凑。</summary>
public sealed class PolygonFields
{

    public float[] Temperature = null!;  // 0..1
    public float[] Moisture    = null!;

    public byte[]  Biome       = null!;  // BiomeType
    public byte[]  Rock        = null!;
    public byte[]  Ore         = null!;
    public int[]   PlateId     = null!;

    public float[] EcologyHealth         = null!;
    public float[] CivilizationPotential = null!;
    public float[] Influence             = null!;
    public short[] PolityId              = null!;  // -1 = 无归属
    public bool[]  BorderMask            = null!;
    public bool[]  TradeRouteMask        = null!;
    public float[] TradeFlow             = null!;

    public int[]   CityId      = null!;  // -1 = 无城市
    public int[]   Downslope   = null!;  // 最陡下降邻居的地块 id，-1 = 入海/洼地
```

### 4.3 索引与坐标约定

| 概念 | 约定 |
| --- | --- |
| 地块 id | `0 .. Count-1`，等于 `Points` 下标 |
| 顶点 id | `0 .. Vertices.P.Length-1` |
| 点坐标 | **源栅格像素空间**（与旧 `[x, y]` 同坐标系），`x ∈ [0, SourceWidth)`，`y ∈ [0, SourceHeight)` |
| 环绕 | 点坐标 x 已归一化到 `[0, SourceWidth)`；`FindCell` 对 x 取模、对 y 钳制 |
| 多边形绕向 | 统一逆时针（CCW），便于描边与半平面填充 |

## 5. 生成方式

### 5.1 插在现有管线的哪一步

`Main.Generation.Driver.cs` 的 `BuildWorldAsync` 里，在**板块生成之后、其他生成器之前**插入建图，在**全部生成器跑完之后**插入采样：

```
1  板块 PlateGenerator                    ← 已有
2  ★ 建多边形网格 PolygonGridBuilder       ← 新增（只用种子 + 尺寸，不依赖任何场）
3  高度 + 地貌掩膜                          ← 已有
4  侵蚀 + 归一化                            ← 已有
5  温度 / 风场 / 湿度                       ← 已有
6  河流 / 群系 / 资源 / 城市 / 统计          ← 已有
7  ★ 栅格 → 地块采样 RasterPolygonBridge   ← 新增
8  ★ 构建邻接/下游/面积 PolygonTopologyBuilder ← 新增
9  渲染（按开关分流）                        ← 已有 + 新重载
```

第 2 步只依赖 `Seed` 与尺寸，可与其他阶段并行；第 7、8 步是 O(cells) 的线性扫描，很快。

### 5.2 取点与尺寸

```csharp
// spacing 由"期望地块数"反推；地块边长与源栅格像素解耦，这是多边形化带来的能力
Spacing = MathF.Round(MathF.Sqrt(SourceWidth * SourceHeight / (float)CellsDesired), 2);
CellsX  = (int)MathF.Floor((SourceWidth  + 0.5f * Spacing) / Spacing);
CellsY  = (int)MathF.Floor((SourceHeight + 0.5f * Spacing) / Spacing);

// 抖动方格：每格一个点，随机偏移 ≤ 0.45 * spacing（避开退化共圆）
radius = Spacing / 2;  jitter = radius * 0.9f;
for (y = radius; y < SourceHeight; y += Spacing)
  for (x = radius; x < SourceWidth; x += Spacing)
      points.Add(new Vector2(WrapX(x + rng(-jitter, jitter)), ClampY(y + rng(-jitter, jitter))));
```

`CellsDesired` 建议档位（新增参数，默认 32,768）：

| 档位 | 地块数 | 256×128 时 spacing | 4096×2048 时 spacing |
| --- | --- | --- | --- |
| 低 | 8,000 | 2.0 px | 32.4 px |
| 中（默认） | 32,768 | 1.0 px | 16.0 px |
| 高 | 65,536 | 0.7 px | 11.3 px |

> 注意：地块边长可以粗于源栅格像素——**栅格负责细节，多边形负责归属**，这是设计意图而非缺陷。若希望地块与栅格同粒度，令 `CellsDesired ≈ W*H/16`（spacing ≈ 4 px）。

### 5.3 环绕处理（本项目特有，必须做）

FMG 用边界伪点裁掉外圈；本项目经度环绕，只靠伪点会让跨缝地块断开。做法：

1. **镜像复制**：把点集扩成三份参与剖分 —— `x - W`、`x`、`x + W`（`W = SourceWidth`）。
2. 取**中间那一份**的拓扑作为结果。
3. 跨缝邻居天然存在：经度 0° 附近的地块，其邻居 id 会落在"中间份"的另一端，直接保留即可。
4. 边界伪点只加在**南北两条纬线**（y = -spacing / y = H + spacing），因为纬度方向不环绕。
5. 代价：Delaunay 输入点数 ×3 → 用空间哈希把插入定位压到均摊 O(1)，或只镜像 1 个 spacing 宽度的邻带（点数 ×1.2 即可，推荐后者）。

### 5.4 从站点到多边形：半平面裁剪 + 顶点校验

**这里与 FMG 的做法不同，是有意为之。** FMG 走 Delaunator 三角剖分再取对偶；本项目改成"用二分面逐个裁剪初始包围盒"。理由有两条：

1. C# 侧没有现成的 Delaunator，自实现 Bowyer–Watson 的邻接维护与退化处理很容易留下隐蔽 bug；
2. **裁剪法的正确性可以自证**——每个多边形角点都能验证"不存在更近的站点切掉它"。于是几何自检可以写成断言，而不是靠肉眼比对。

| 步骤 | 说明 |
| --- | --- |
| 初始包围盒 | 横向以站点为中心、宽一个环绕周期；纵向就是地图上下边界（极圈是硬边） |
| 逐条裁剪 | 按候选距离**升序**用二分面裁剪：保留"到本站点不比到候选站点远"的一侧（`p·(q−p_i) ≤ (|q|²−|p_i|²)/2`） |
| 提前退出 | 二分面到站点的距离是候选距离的一半。一旦它 ≥ 当前多边形最大顶点半径，该面切不到多边形，更远的候选更不可能——**这是精确判据，不是启发式** |
| 顶点校验 | 逐角点查"是否存在更近的站点"。有则说明候选集漏了它，补上该站点的**全部镜像副本**后重裁。正常情况下零轮补裁 |
| 冗余顶点清理 | 去掉重复顶点与共线顶点（容差 1e-7px）：裁剪会在近乎相切处留下多余的共线点，它不影响形状却让顶点数虚高、拖慢光栅化 |
| 邻接提取 | 每条非极边的中点，取最近的"非自身"站点。Voronoi 边上任意一点到两侧站点等距，所以共享该边的邻居必然被选中 |
| 面积/质心 | 鞋带公式；面积是旧栅格模型里不存在的维度 |
| 复杂度 | 期望接近 O(地块数)；抖动方格下每个地块实际只用到 8~14 个候选 |

**实测（32768 地块）**：补裁 0、退化 0、校验失败 0；面积覆盖率 100.0000%。

> 已否决的替代方案：Bowyer–Watson 增量三角剖分 + 取对偶。核心障碍不是性能，而是"退化情形下的邻接正确性无法自证"——一旦邻接错了，河流与文明扩散会静默走偏，而这正是本改造最不能出的错。

### 5.5 采样规则（栅格 → 地块）

| 属性类型 | 采样方式 | 理由 |
| --- | --- | --- |
| 连续量（高度、温度、湿度、河流、生态、文明影响、贸易流） | **多边形面积加权平均** | 保留梯度，避免地块边缘跳变 |
| 离散量（群系、岩石、矿产、板块 id） | **质心采样** | 避免混色/混类；一个地块只能是一个群系 |
| 河流 | 面积加权 + 与邻接比较取 `max` 的混合（`α·mean + (1-α)·max`，α=0.7） | 河道很细，纯平均会被稀释到看不见 |
| 城市 | 城市点 → `FindCell(城市坐标)`，写入 `CityId` | 城市从"格子坐标"升级为"地块归属" |
| 面积 | 直接来自多边形 | 新增维度，旧系统没有 |

**机制二：双向桥（核心，已实现）**

```csharp
public static class RasterPolygonBridge
{
    // 栅格 → 地块
    public static void SampleContinuous(PolygonCellMap map, float[,] raster, float[] destination);
    public static void SampleDiscreteAtCentroid(PolygonGrid grid, PolygonCellMap map, byte[,] raster, byte[] destination);
    public static void SampleRiver(PolygonCellMap map, float[,] raster, float[] destination, float meanWeight = 0.7f);

    // 地块 → 栅格
    public static void SplatFloat(PolygonCellMap map, float[] source, float[,] destination);
    public static void SplatByte(PolygonCellMap map, byte[] source, byte[,] destination);
    // …其余属性同构

    // 点归属（城市、地标）
    public static void AssignPointsToCells(PolygonGrid grid, ReadOnlySpan<int> pointX, ReadOnlySpan<int> pointY, int[] cellOfPoint);
}
```

关键在于**两个方向共用同一张 `PolygonCellMap`（像素归属图）**，因此互为逆运算：
`SampleContinuous(SplatFloat(x)) == x` 严格成立（自检里逐位验证过）。
归属图由 `PolygonRasterizer.BuildCellMap` 用扫描线填充一次性建好，之后每次采样/投影都只是数组索引，没有几何运算。

旧消费者（`StatsCalculator`、`WorldRenderer` 的逐像素渲染、小地图）拿到投影后行为完全不变。

> 实现细节：`Splat*` 采用"原地填目标栅格"而不是"返回新数组"，
> 因为调用方通常已经有 `float[,]` 缓冲，返回新数组会在 4096×2048 下多一次 33 MB 的分配。

**机制三：缓存版本升级**

```csharp
private const int WorldGenerationAlgorithmVersion = 4;  // 由 3 → 4，旧缓存自动失效
```

`PersistedWorldData` 新增 `polygons` 段。为控制体积，**只存 `Points` + `Boundary` + `CellsDesired`**，加载时用同一套 Delaunay 重建 `cells/vertices`（FMG 的 `rebuildGraph` 思路）。代价：约 8 字节/地块，而不是存全部拓扑。

### 7.1 两条渲染路径

**路径 A：多边形光栅化（保底，输出仍是 `Image`）**


- 对每个地块：扫描线填充其多边形（或半平面裁剪）。
- **复用现有配色**：`DrawSatellite / DrawElevation / DrawBiomeColor / DrawCivilizationColor …` 全部保留，只是调用者从"逐像素"变成"逐地块一次"，颜色由地块属性算出。

- 抗锯齿默认关闭（保持现有像素风）；需要时用 4× 超采样再降采样。
- 与 `_lastRenderedImage` 兼容 → **PNG 导出、小地图、图例零改动**。

**路径 B：矢量绘制（体验升级）**

### 7.2 图层归属（P3 + P4 已实现）

**默认模式 `Cells` 下，游戏地图就是多边形单元格**：所有能按地块属性着色的图层都用多边形填充，
连续场在这里是"逐地块取一个采样值再平铺"。

| 图层 | `Cells` 模式 | 说明 |
| --- | --- | --- |
| Biomes / RockTypes / Ores / Landform / Plates | **多边形** | 离散分类，一个地块一种取值 |
| Satellite / Temperature / Moisture / Elevation / Rivers | **多边形** | 连续场按地块采样值平铺；失去逐像素渐变，换来地图构成单元与地块模型一致 |
| Ecology / Civilization / TradeRoutes | **多边形** | 数据源已地块化（P4 第二阶段）；文明侧含政体色、边界提亮、贸易走廊叠加 |
| Cities | 栅格 | 需要地形总览做背景，是"半连续 + 标记"的混合图层 |
| Wind | 栅格 | 需要在地图上叠加箭头（栅格侧最后一个图层） |
| PolygonGrid（地块划分） | 线框 | 中性底色 + 边界，专用于观察地块划分本身 |

`Hybrid` 模式下只有第一行那五个离散分类图层走多边形，其余全部栅格——这是"保守"档，用于对照。

"地块划分"图层在 P3 改成了**中性底色 + 边界线框**——它不再按属性着色（那与"生物群系"等图层重复），
专门用来看地块划分本身：网格是否均匀、边界是否连续、经度缝处是否接得上。


## 8. 交互调整（P2 已完成）

### 8.1 统一入口：一次采样

改造前拾取是"局部坐标 → 纹理比例 → 像素下标"，交互单元就是像素。改造后所有交互都先经过一个统一入口：

```csharp
private bool TrySampleAtLocalPosition(Vector2 localPosition, out CellSample sample);
```

`CellSample` 把"鼠标落在哪里"统一成地块或像素两种来源，下游的叙事、威胁评估、悬停面板、Oracle 只吃这个结构——
因此**两条路径不需要各写一份逻辑**，回退也不会产生第二套行为。

| 交互 | 改造前 | 改造后 |
| --- | --- | --- |
| 拾取 | `(int)(tX * MapWidth)` 像素下标 | `grid.FindCell(tX * MapWidth, tY * MapHeight)`——精确的最近站点查询，均摊 O(1) |
| 拾取精确性 | 像素是"格子"，边界处天然有歧义 | "最近站点"与"点落在哪个多边形内"**严格等价**，结果不可能落到多边形之外 |
| 悬停面板 | 群系/地貌/坐标/高度/温度/湿度/河流 | 追加 **地块编号、面积、邻接数**，以及"贴极圈""跨经度缝"两个只有地块模型才有的标记 |
| 悬停高亮 | 只有信息面板，地图上无视觉反馈 | **沿多边形描边 + 半透明填充**（`MapCellOverlay`） |
| 点击选中 | 传 `sampleX/sampleY` 像素坐标 | 传 `CellSample`；叙事文本里标出"地块 #N" |
| Oracle 区域分析 | `world.Biome[x, y]` | 优先读 `Fields.Biome[cell]`，并**自校验**缓存的地块编号是否仍对应同一锚点，不匹配就退回像素路径 |
| 城市列表 | 只有像素坐标 | 追加"→ 地块 #N"，城市与地块的归属关系第一次在界面上可见 |
| 缩放/平移/小地图拖拽 | 基于纹理 UV | **零改动**（不涉及地块） |
| 区域选择（新增能力） | — | `FindAll(x, y, radius)` 沿邻接做环形 BFS，为后续"刷选地块、标记领地"打底 |

### 8.2 悬停高亮的实现要点

高亮最难的一处是**跨经度缝的地块**：它的顶点在"未展开帧"里散落在 x ≈ 0 与 x ≈ Width 两侧，直接连起来会被拉成横贯整张图的细条。做法是：

1. 把每个顶点平移到"离质心最近"的镜像副本，得到一个连续的本地多边形；
2. 再整体按 `0 / −Width / +Width` 各输出一份；
3. 缝上的地块必然有一份落在画布内，超出的部分交给一个带 `ClipContents` 的容器裁掉。

这样**不需要在多边形层面做缝切分**。几何部分（`PolygonGrid.GetHighlightRings`）放在 Godot 无关的核心层，因此能被自检覆盖（见 §11.6）。

覆盖层挂成 `MapTexture` 的子节点，局部坐标系就是纹理空间，与缩放的祖先节点（`MapAspect` 的 `Scale`）完全解耦，不需要任何全局变换换算。

> **仍未地块化的部分**：地貌分类（`ClassifyLandform`）依旧依赖 8 邻域像素统计，交互路径上取地块质心所在的像素来保持口径一致。把它改成用 `Cells.C` 的真实邻接是 P4 的事——那时的判据会从"8 个固定方向"变成"真实的多边形邻居"，是有意义的改进，但也需要单独验证。

## 11. 验证方案与 P0 实测结果

### 11.1 几何自检（已实现，`PolygonGridValidator`）

| # | 判据 | 为什么是它 |
| --- | --- | --- |
| 1 | 每个地块角点数 ≥ 3，面积 > 0 | 抓裁剪退化与绕向错误 |
| 2 | **面积守恒**：`Σ Area == 地图面积`（容差 1%） | 一次性抓出"漏裁""重复覆盖""点阵有空洞"三类错误 |
| 3 | **凸性**：每个多边形必须凸 | Voronoi 单元的充要几何性质；非凸即裁剪有误 |
| 4 | **邻接对称**：`j ∈ C[i] ⇔ i ∈ C[j]`，无自邻接，邻接数 ≥ 2 | 抓邻接提取错误 |
| 5 | **边归属**：每条非极边的归属站点必须出现在邻接表中 | 几何与拓扑互相印证 |
| 6 | **边数结构**：`顶点数 == 邻接数 + 极边数` | 多边形的每条边要么对应一个邻居，要么整条落在南北硬边界上 |
| 7 | **镜像点生效**：无顶点落在初始包围盒的经度边界上 | 镜像点失效时包围盒的 x 边会变成多边形的一条边，立刻报警 |
| 8 | **拾取一致性**：随机 2 万点，`FindCell` 结果必须真的包含该点 | Voronoi 单元 = 最近站点区域，两者严格等价 |
| 9 | 站点与质心自包含 | 抓"多边形与站点错位" |

> **一条被否决的判据**：最初写的是"最左列与最右列必须互为邻居"，实测有 3 个地块不满足。诊断后发现**是判据错了**：同列上下行的站点可能抖动到最左，把中间地块的左边夹住，于是该地块根本不与最右列相邻——这是合法的环面铺砌。面积覆盖率同时精确等于 1.000000，证明拓扑本来就是对的。这条经验写进了 §12 风险表。

```
── 1e. 多边形渲染（离散分类图层） ──
```

## 14. P0 实施记录

### 14.1 做了什么

新增 8 个文件（约 2400 行，全部带中文注释），**没有改动任何既有文件**，因此原有功能不受影响：

- 抖动方格取点（点距取整成能整除地图尺寸的值，使点阵在经度方向严格周期，缝两侧点距与其他位置完全一致）
- 半平面裁剪 + 顶点校验的 Voronoi 建图
- 桶索引（含经度环绕镜像）与 O(1) 精确拾取
- CSR 扁平化的多边形与邻接存储、面积与质心
- 拓扑派生：下游方向（按单位距离落差择优，取代硬编码 8 邻域）、汇流量、环形扩展、连通分量
- 几何自检器（产线的一部分，不是测试脚手架）

### 14.2 自检抓到的四个真问题

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 3 个地块"没有跨缝邻居" | **判据本身错了**：同列上下行站点抖动到最左会把中间地块夹住，它本来就不该与最右列相邻 | 换成结构性判据（边归属 + 边数结构 + 包围盒顶点），见 §11.1 判据 5/6/7 |
| 2 | 2×2 极小地图面积覆盖率 1.32 | `MirroredPosition` 只取"最近的一个镜像副本"；周期小时两个镜像可能等距，漏掉一侧约束 | 改为枚举全部镜像副本（`CollectImages` / `CollectWithin`） |
| 3 | 极小地图顶点数 != 邻接数 + 极边数 | 裁剪在近乎相切处留下冗余共线顶点 | 裁剪后统一清理重复与共线顶点 |
| 4 | **邻接表全空**，但多边形、面积、拾取全部正确 | `SiteIndex.FindNearest` 把**平方距离**当距离返回；`ExtractNeighbors` 里"归属距离 > 自身距离"因此永远成立，所有边被跳过。`FindViolator` 同理会漏判 | 返回 `Math.Sqrt`；同时把逐环搜索的停止判据改成同量纲的平方比较 |

第 4 条最值得记住：它的症状是"看起来一切正常，只有邻接表是空的"。如果只做面积/拾取这类检查，它会一路混到 P4 才以"河流不走"的形式暴露出来。

### 14.3 本机工具链绕行说明（重要）

本机非交互 shell 里 NuGet 解析不到用户配置路径（`dotnet nuget locals all --list` 单独执行也报 `Value cannot be null. (Parameter 'path1')`），导致：

- `dotnet build PlanetGeneration.csproj` → `无法解析 SDK "Godot.NET.Sdk"`
- 任何带包依赖的工程都无法还原

自检工程没有任何 NuGet 包依赖，因此在 `PolygonSelfTest.csproj` 里用**显式 `Sdk.props` / `Sdk.targets` 导入**，并在 SDK 目标之后把 `ResolvePackageAssets`、`ResolvePackageDependenciesForBuild`、`GenerateBuildDependencyFile`、`GenerateBuildRuntimeConfigurationFiles` 覆盖成空目标，同时手工提供 `PolygonSelfTest.runtimeconfig.json`。

构建与运行：

```bash
# 本机（绕行方式）
cd tools/polygon-selftest
dotnet build PolygonSelfTest.csproj --no-restore -p:RestoreProjectStyle=None
dotnet bin/Debug/net10.0/PolygonSelfTest.dll
dotnet bin/Debug/net10.0/PolygonSelfTest.dll edges   # 逐边诊断

# 环境正常的终端
dotnet run --project tools/polygon-selftest
```

在环境正常的终端里，可以把上面那四个空目标与手工 runtimeconfig 删掉，恢复标准行为。

**补充结论（P2 期间确认）**：这个环境问题会**传递给子进程**——
从本会话启动 Godot 并执行 `--build-solutions`，报的是同一个 `无法解析 SDK "Godot.NET.Sdk"`；
显式补 `APPDATA` / `LOCALAPPDATA` 能修好 Godot 的 `user://` 解析，但修不好 NuGet 的配置加载
（NuGet 走的是 Win32 API 而不是环境变量）。
因此**任何从这个会话发起的 Godot 构建都不可用**，只能在用户自己打开的编辑器里构建。
证据是 `.godot/mono/temp/bin/Debug/PlanetGeneration.dll` 在 P2 期间被更新过一次——那次来自用户自己的编辑器。

### 14.4 P1 实施记录

**做了什么**

1. **双向桥**（`RasterPolygonBridge` + `PolygonRasterizer`，约 660 行，Godot 无关）
   - 像素归属图是栅格与地块之间的**唯一接缝**，采样与投影共用它，因此互为逆运算；
   - 采样分三档：连续量面积加权、离散量质心、河流 mean/max 混合；
   - 投影（`Splat*`）按需把地块属性写回栅格，供尚未迁移的旧消费者使用——这是 P4 才真正用到的兼容通道，但机制先建好并验证了。

2. **接线**（9 个既有文件，全部是接线级小改）
   - 新增"地块划分"图层（复用生物群系配色 + 地块边界描边），用来和栅格版生物群系图层做 A/B 对照；
   - 地块层在全部栅格生成器之后构建，模式为 `Raster` 时零开销；
   - 设置持久化 `PolygonTileModeId` / `CellsDesired`，但**没有加 UI 控件**——新图层走既有数据驱动图层列表，不需要改场景文件。

3. **两个验证工具**
   - `tools/godot-typecheck`：Godot 工程的类型检查（见 §11.4）。这是本轮最重要的基础设施——**没有它，改 Godot 侧接线就是盲改**。
   - `tools/polygon-selftest/PreviewRenderer.cs`：离线渲染栅格版与多边形版对照图，不启动 Godot 就能肉眼验证。

**本轮抓到的两个问题**

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 光滑场投影最大误差 0.478，远超理论上界 0.018 | **测试场的问题**：用线性梯度会让缝两侧取值从 1.0 跳到 0.0，跨缝地块覆盖了整整一个值域。换成经度方向周期的正弦场后误差落回界内。教训：跨缝测试必须用周期场 |
| 2 | "河流混合确实提升可见度"失败（只有 2716/8192 个地块被抬升） | **判据的问题**：只有约 1/3 的地块真的含河道像素，其余地块三种算法都得 0。判据应只针对含河道的地块 |

**关键结论**：地块层属性与栅格的一致性达到 98.6%（8192 地块）／97.6%（2048 地块），差异全部集中在多边形边界，符合"一个地块只有一种群系"的设计意图。地块数量越多，边界占比越小、一致性越高——这与预期完全一致。

**已知可优化项**：对比模式（A/B 双世界）下两个世界各建一次地块图，而地块图只依赖 `(宽, 高, 种子, 目标地块数)`，两者完全相同。多花约 300ms，暂不处理；若要优化，可把几何（`PolygonGrid`）与属性（`PolygonFields`）拆开，让几何被两个世界共享。

**注意**：Godot 工程本身的编译验证仍需在 Godot 编辑器或你自己的终端里做；本次只验证了地块核心（Godot 无关部分）的编译与运行。
（P2 起 `tools/godot-typecheck` 已经能对 Godot 工程做类型检查，见 §11.5。）

### 14.5 P2 实施记录

**做了什么**

1. **统一采样入口**（`CellSample` + `TrySampleAtLocalPosition`）
   - 把"鼠标落在哪里"统一成地块或像素两种来源，下游的叙事、威胁评估、悬停面板、Oracle 只吃这个结构；
   - 因此 `Raster` 回退路径与地块路径**共用同一份展示逻辑**，不会出现"回退后文案不一样"这种隐蔽分叉。

2. **拾取改为地块优先**
   - `grid.FindCell(tX * MapWidth, tY * MapHeight)`——精确的最近站点查询，均摊 O(1)；
   - "最近站点"与"点落在哪个多边形内"严格等价（20 万点验证过），所以拾取结果不可能落到多边形之外。

3. **悬停高亮**（`MapCellOverlay` + `PolygonGrid.GetHighlightRings`）
   - 跨经度缝的地块：顶点先平移到离质心最近的镜像副本，再按 `0 / ±Width` 各输出一份，超出的由 `ClipContents` 容器裁掉；
   - **不需要在多边形层面做缝切分**，这是本轮最省事也最稳的一处设计；
   - 几何放在核心层，所以能被自检覆盖。

4. **Oracle 自校验**
   - 缓存的地块编号必须满足 `FindCell(锚点) == 缓存编号` 才使用，否则退回像素路径。
   - 这样重新生成世界（种子变了就是另一张地块图）后不需要到处埋重置逻辑。

**本轮抓到的问题**

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 编译报"成员声明中的标记 } 无效" | 替换 `ResetBiomeHoverState`/`TrySampleBiome`/`BuildBiomeHoverText` 时，新块里带上了类结束花括号，而原 `UpdateLoreFromMapSelection` 还在文件末尾 → 重复定义 + 花括号错位。**类型检查当场拦下** |
| 2 | 点击非"生物群系/地貌"图层时，Oracle 的"最近选定区域"不再更新 | 改造前这条链路藏在 `TrySampleBiome` 里（它被 `UpdateLoreFromMapSelection` 调用，与图层无关）；重构时随方法一起被删掉了。**这是纯粹的行为回归，靠读代码发现，不是靠测试** |

第 2 条值得记：重构时把逻辑从一个"碰巧被共用"的私有方法里搬走，很容易漏掉那些隐式依赖它副作用的调用点。后续如果还要做这类搬迁，应该先列出该方法的全部调用点与副作用。

**关键结论**：P2 完成后，鼠标交互（拾取/悬停/选中/Oracle）已全部以地块为单位，而渲染仍走栅格——这正是"混合模式"的设计意图：交互先享受地块模型的精度，渲染按图层逐步接管（P3）。

### 14.6 P3 实施记录

**做了什么**

1. **多边形渲染接管 5 个离散分类图层**（Biomes / RockTypes / Ores / Landform / Plates）
   - 判据是"离散分类 vs 连续场"：离散量一个地块只有一种取值，多边形填充不会在格子边界混色；连续场靠逐像素渐变与等值线表达信息，地块化会把这些细节抹平；
   - 两条路径**共用同一套配色**（`WorldRenderer` 只开放取色函数，`DrawPlates` 与 `GetPlateColor` 共用实现），所以差异只可能来自几何，不可能来自调色——这是 A/B 对照的前提。

2. **模式枚举重新定义**：`Raster`（全部栅格）/ `Hybrid`（离散图层多边形，默认）/ `Outlined`（再加边界描边）。
   三个取值都有实际行为差异，没有占位项。原来的 `PolygonOnly` 是个空壳，改名并赋予真实语义。

3. **"地块划分"图层改为线框视图**（中性底色 + 边界）
   - 它原来按生物群系着色，与"生物群系"图层完全重复；改成线框后专用于观察地块划分本身：网格是否均匀、边界是否连续、经度缝处是否接得上。

4. **`PolygonFields` 扩充**：新增 `Landform`（质心分类）与 `PlateBoundary`（质心采样），支撑地貌与板块两个图层。

**本轮修正的一处判据错误**

最初想断言"多边形渲染与栅格渲染的差异像素必须全部位于地块边界"。写下来才意识到那是错的：
差异出现在**分类块边界**上（一个地块横跨两个分类块时只能取质心那一个分类），与地块边界无关。
正确做法是把判据落在"多边形渲染自己的定义性属性"上——**同一地块内像素颜色完全一致**（不混色），
而不是拿栅格渲染当基准。这条与 P0 那次"环绕判据写错"是同一类错误：**判据必须能被证伪，且不能把另一个实现当真理**。

**未做的两件事（都推迟到 P4，理由写进 §7.4）**

- **增量重绘**：前提是模拟本身地块化。现在的生态/文明模拟是逐像素整场重算，拿不到"哪些地块变了"。
- **`PolygonPathBuilder`（矢量路径）**：目前没有真正的消费者。悬停高亮用 `GetHighlightRings` 已经够用，
  真正需要矢量路径的是 P4 的河流折线与政体边界。先造一个没有消费者的抽象只会变成负担。

**关键结论**：P3 之后，"多边形"从交互层走到了渲染层——5 个离散分类图层已经是多边形填充。
剩下的 `Ecology` / `Civilization` / `TradeRoutes` / `Rivers` / `Cities` 之所以还留在栅格，
原因不是渲染层做不到，而是**它们的数据源还在逐像素的模拟器里**。这正好把 P4 的目标指清楚了：
**把模拟搬到地块上，渲染自然就能跟上。**

### 14.7 P4 第一阶段实施记录

**做了什么**

1. **地貌分类地块化**（`PolygonLandformClassifier`）
   - 用 `Cells.C` 的真实多边形邻接替代栅格版的 8 邻域像素统计；
   - 阈值与栅格版逐条对应，只做了一处必要调整：**邻接数不是固定的 8**（抖动方格下是 5~7），
     所以"有多少个邻居更高/更低"这类判据改成按**比例**比较，否则地块会因为邻居少而永远达不到阈值；
   - 图层与悬停面板现在读的是**同一份**分类结果，不可能出现"图层画的和悬停说的不一致"。

2. **河流地块化**（`PolygonRiverBuilder`）
   - 在**地块图**上按最陡下降方向累积排水面积与湿度加权汇流量，一次降序遍历即可，无需迭代收敛；
   - 与栅格版的根本区别：栅格版是"从源头随机游走 + 8 方向择优"，河道方向受像素栅格约束；
     地块版是"全域累积"，河道沿真实的多边形邻接流动，不受 8 方向限制。

3. **地图单元格化**：新增 `PolygonTileMode.Cells` 并设为默认
   - 所有能按地块属性着色的图层都用多边形填充（地形总览 / 板块 / 温度 / 河流 / 湿度 / 高程 / 岩石 / 矿产 / 生物群系 / 地貌）；
   - 为此给 `WorldRenderer` 补了 4 个取色接口（`GetSatelliteColor` / `GetTemperatureColor` / `GetMoistureColor` / `GetRiverColor`），
     并把 `DrawSatellite` 重构成"极区掩膜作为参数"的形式，让逐像素与逐地块共用同一份实现；
   - 剩下 `Ecology` / `Civilization` / `TradeRoutes` / `Cities` / `Wind` 留在栅格，原因写在 §7.2 的表里。

**本轮靠离线预览图发现的一个真问题（值得记住）**

第一版河流按**汇流量的分位数**取阈值。自检全绿——河道不断裂、可达水体、占比正确——
但预览图上一眼就看出：**河道全挤在海岸线上，不向内陆延伸。**

原因是汇流量沿程单调递增，取它的分位数就等于取"离海最近的那一批"。
自检之所以没抓到，是因为我断言的每一条它都满足：河道确实连通、确实流向大海、占比确实对。
**"正确但不像河"这类问题，只有看图能发现。**

修法：阈值改成按**排水面积**（有多少地块的水从这里流出去）取分位数。
排水面积同样单调递增、所以连通性判据依然成立，但它的分布更能区分"干流"与"支流"，
河网会自然向内陆延伸。

**顺带发现的第二件事**：合成地形如果是**径向穹顶**（水从峰顶向四周辐射流走），
只会形成一圈小流域，无论阈值怎么调都出不来长河。所以自检与预览用的合成地形都必须加多倍频噪声——
否则测的是一张"永远长不出河"的地形，得到的结论没有意义。

**关键结论**：`Cells` 模式落地后，**游戏地图已经是多边形单元格**。
数据侧还差最后一块——生态与文明两个模拟器仍是逐像素的，
它们决定了 `Ecology` / `Civilization` / `TradeRoutes` 三个图层能否多边形化，以及增量重绘能否实现。
这块单独占 P4 的剩余部分。

### 14.8 P4 第二阶段实施记录（生态与文明模拟地块化）

**做了什么**

1. **生态模拟地块化**（`PolygonEcologySimulator`）
   - 逐地块计算生态健康与文明潜力，公式框架与栅格版一致；
   - 唯一实质改造是**地形稳定性判据**，见下面「本轮最重要的修正」。

2. **文明模拟地块化**（`PolygonCivilizationSimulator`，约 1000 行）
   - 三类必须改造而非机械平移的运算：
     - **邻域**：硬编码 8 邻域 → `grid.CellNeighbors` 真实邻接；"有几个外国邻居"改成按比例；
     - **扩张评分**：`sqrt(dx²+dy²)` → `grid.WrappedDistance`（测地距离）；
     - **贸易走廊**：像素直线光栅化 → 沿真实邻接的 Dijkstra 最短路（代价含地形起伏与海陆惩罚）。
   - 射程量纲从**像素**改为**地块圈数 × spacing**：这是唯一必须偏离栅格版的地方，
     详见 §14.9 的三次踩坑记录。

3. **渲染层接线**
   - `ShouldRenderAsPolygon` 的排除列表从 `{Civilization, TradeRoutes, Wind}` 缩到只剩 `{Wind}`；
   - `WorldRenderer` 补 `GetCivilizationColor` / `GetTradeRouteColor` 两个公开取色接口，
     与逐像素路径共用同一份实现（配色不可能分叉）；
   - `Main.Rendering.cs` 的两个信息栏分支按 `ShouldRenderAsPolygon` 分流；
   - `Main.Handlers.cs` 的 `InvalidateEcologyCaches` 补上 `PolygonCivilization` 的失效。

**本轮最重要的修正：内陆环状空心（又一个「自检全绿但图不对」的案例）**

文明模拟跑通后，自检 13 条判据**全部通过**，数字看起来也合理
（政体 12 个、控制率 58.7%、贸易走廊 175 块、枢纽联通率 100%）。
但离线预览图上，**大块内陆是深灰未声明**，领土沿着海岸和河流形成一圈环。

这种"判据都对、图不对"的形态与 P4-a 的河流问题、P3 的差异判据问题同源，
所以这次没有先调参，而是**先造诊断**（`DiagCivilization`）：

```
入海距离桶   块数   平均影响力   平均高程   平均潜力
1 圈          221   0.3318      0.5419     0.5904
3 圈          101   0.2161      0.7192     0.4163
6 圈            9   0.0967      0.8351     0.2927
沿海：159/221 被声明（71.9%）
内陆：121/352 被声明（34.4%）
```

诊断先排除了一个错误假设。最初的怀疑是**地形惩罚过重**（评分里乘了 `1 - terrainPenalty*0.42`），
因为它用**全场最大高程**归一化——若地图有座高峰，内陆惩罚会被放大。
实测否定了这个假设：地形阻尼只有 0.58~0.77，单靠它远不足以解释。

于是做**判定实验**：按同一公式重算，但把 `distanceFactor` 强行置 1（等价射程无穷大）。结果：

```
高原（高程 > 0.70）：163 块，可达上限越阈值 15 块（9.2%）
```

**即使射程无穷大，高原也只有 9.2% 能越过阈值。** 这证明瓶颈与距离无关，
而是**评分是乘性链、天花板本身就低于阈值**：

```
score = localSupport × terrainDamp × distanceFactor × ...
```

每个因子单看都温和（0.58 / 0.77 / 0.86），相乘后整体跌破 0.2588。
这就是**乘积陷阱**——而且它有个恶劣性质：**任何单项调参都救不回来**，
因为你把某一项从 0.58 提到 0.7，乘积只涨一点，仍越不过阈值。
（如果不是先做这个判定实验，我很可能会在"调射程"和"调地形惩罚"之间反复试错。）

**真正的根因有四个，逐个修掉：**

| # | 问题 | 性质 |
|---|------|------|
| 1 | 海拔被惩罚两次：`terrainAdaptation`（内含地形项）与 `1 - terrainPenalty*0.42` 同时挂在乘性链上 | 乘积陷阱 |
| 2 | `terrainStability = 1 - heightFromSea^1.25` 把"高"等同于"不宜居"，高原稳定性掉到 0.47 | 判据本身错了 |
| 3 | `localSupport = potential*0.72 + riverFactor*0.28` 让无河内陆的潜力被无条件打七折 | 继承自栅格版的偏置 |
| 4 | 兜底撒点门槛固定 `potential >= 0.62`，而高原潜力只有 0.21~0.30 → **高原上永远播不下种子** | 死条件 |

修法与理由：

1. **海拔只惩罚一次**，删掉评分链上的 `(1 - terrainPenalty*0.42)`，海拔只通过 `terrainAdaptation` 起作用。
2. **稳定性改看"局部起伏"而非"绝对海拔"**：新增 `ComputeRuggedness`，
   用真实邻接取相邻地块平均高差（归一化标尺 0.18）。
   真正阻碍定居的是地形起伏，不是绝对高度——平坦高原（安第斯、青藏谷地）完全能承载稠密文明。
   这恰好是**地块模型才有的能力**：栅格 8 邻域里斜对角距离是 √2 倍，高差不能直接平均。
3. **河流是加成，不是必要条件**：`potential` 系数 0.72 → 0.88，河流保留 0.12 作纯加成，
   再乘一个 `1 + riverFactor*0.10` 的小加成。临河依然明显优于不临河，但不临河不再被罚出阈值。
4. **播种门槛随海拔放宽**：`0.62 → 0.62 - altitudeT*0.32`（高原下限 0.30）。
   低地仍要求优质（保持"良田优先"），高海拔按比例放宽——
   山地上确实存在以牧业/矿业为生的政体，只是密度低。

**修正效果（合成网格 573 个陆地块）**

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 内陆平均影响力 | 0.2212 | 0.4922 |
| 沿海声明率 | 71.9% | 97.3% |
| 内陆声明率 | 34.4% | 79.3% |
| 控制率 | 48.9% | 86.2% |
| 影响力为 0 的地块 | 77 块 | **0 块** |

预览图上**环形空心彻底消失**，内陆被完整填充，只剩最高峰处（海拔 >0.7 的极陡山脊）
保留少量深灰块——那是合理的"不宜居山脊"，不再是整块高原留白。

**顺带抓到的两个回归（都由新判据/自检发现）**

- **距离衰减矫枉过正**：第一版把 `d<=R` 的平台期给成常量 1.0，
  射程内完全不衰减 → 强政体一路碾压，政体数从 14 掉到 **8**、单块领土吃掉整个大陆。
  改成 "平台期 0.82~1.0 线性缓降 + 尾部幂次衰减" 后回到 10 个政体。
  **"让内陆可被填充"和"保留政体竞争"是同一式子上的两个要求**，必须同时满足。
- **零领土政体破坏编号不变量**：距离衰减改缓后出现"某个弱种子一个地块都没抢到"，
  于是 `polityIdMap` 里出现编号 ≥ `PolityCount` 的值，自检「政体编号在范围内」当场报错。
  我第一版修法是在评分阶段给发祥地加保底（`BirthplaceHoldBonus`），**方向错了**：
  它只是把归属阶段与纪元阶段强行对齐，结果纪元动态仍能造出零领土政体，
  而且保底让本该被吞并的政体活了下来，**破坏了"纪元推进 → 政体数不增"的单调性**
  （自检报"纪元 0/450/900 政体数为 12/13/13，出现反弹"）。
  正确修法是把不变量做在**出口处**：所有会改动归属的环节跑完后统一 `RenumberPolities`，
  剔除零领土政体、把编号压紧成 0..N-1。**不变量由结构保证，而不是靠各环节自觉。**

**关键结论**：P4 数据侧到此完成。`Ecology` / `Civilization` / `TradeRoutes`
三个图层已走多边形渲染，栅格侧只剩 `Wind`。增量重绘的解锁条件已具备。

### 14.9 量纲改造：射程为什么必须从"像素"改成"地块圈数"

这是整个 P4 第二阶段里**唯一一处必须主动偏离栅格版**的设计决定，也踩了两次坑。

**问题**：栅格版的 `expansionRange = Lerp(10, 48, epochFactor)` 是**像素**量纲。
搬到地块图上照抄会坏掉，因为地块边长（`spacing`）随地图尺寸与目标地块数变化——
实测在 4~16 px 之间。于是同一个 `48`：

- 在细地块图上覆盖 12 圈地块；
- 在粗地块图上只覆盖 3 圈。

**同一套参数在不同地图上表现完全不同**，这正是"像素量纲"的根本缺陷。

**解法**：把射程定义成**地块圈数**，再乘 `spacing` 换算回像素：

```csharp
var spacing = Math.Max(grid.SpacingX, 1e-6d);
var expansionRings = Lerp(3.5f, 11f, epochFactor) * Lerp(0.82f, 1.2f, diversityNorm);
var expansionRange = (float)(expansionRings * spacing);
```

于是"政体能扩张多远"始终是"约多少圈邻居"，与分辨率、地块密度都无关。
这比"隐式依赖像素"更正确，也是地块模型相对栅格模型的**真实收益之一**。
同样的改造施于：贸易射程（`Lerp(6, 22, ...)`）、种子间距（`spacingRings`）、
贸易走廊的地形代价。

**两次踩坑**：

1. **只换算一边**：第一次把 `expansionRange` 除以 `spacing`，
   却忘了同时归一化距离。结果射程缩到 `1/spacing` 而距离仍是像素值，
   `distanceFactor` 直接归零——症状是「政体只有 4 个、控制率 1.6%」。
   **两边必须同时换算**，这是量纲一致性的基本要求，但很容易只改一处。
2. **射程改对了，但评分公式的假参数还在**：射程量纲修正后控制率回到正常，
   却在预览图上暴露出内陆环状空心（§14.8）——说明"数值看起来正常"不等于"结构正确"。

**教训**：量纲错配的症状往往是**极端的数值异常**（控制率 1.6%），
而结构性缺陷的症状是**数值正常但图形不对**。两者的诊断路径完全不同：
前者检查单位换算，后者需要造**判定实验**去分离变量（如把 `distanceFactor` 置 1）。
